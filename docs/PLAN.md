# PLAN

> 这份文档写在动手之前，描述这个项目**打算怎么做**。随着开发推进会不断更新：
> 完成的阶段标记结果，没做的阶段保持原样。

---

## 一、要解决的问题

web_ics 支持客户端证书认证，开启它的步骤写在 ICS 仓库 README 的「开启客户端证书认证」一节，
是一串 openssl 命令：建 CA、签服务器证书、给每台设备签客户端证书、导出浏览器能装的证书包、
维护吊销名单、改配置文件。

这条路径有几个麻烦：

1. 命令长、参数多，输错一个字符要等到浏览器握手失败才发现；
2. 证书参数有隐含要求（SAN 不能为空、`KeyUsage` 要有 `digitalSignature`、
   子证书有效期不能超过 CA），漏了不会有明显报错，只会「证书不受信任」；
3. 给十几台设备签证书要重复十几遍，每次都要改 CN 和输出文件名；
4. 导出 `.pfx` 的参数不对时，Windows 会把私钥塞进老式加密提供程序，浏览器递不出证书，
   而现象是「点了确定没反应」；
5. 吊销名单的格式与 web_ics 的解析口径绑定，手写容易写错，写错会让服务拒绝启动。

**目标**：把这套流程做成一个 Windows 上的图形化工具，让不熟悉 openssl 的人也能正确签出一套
web_ics 认的证书。

---

## 二、范围

### 打算做的

- 生成内部 CA（自签名，单层结构），也支持导入已有的 CA
- 签服务器证书，内网地址与外网地址都进 SAN
- 签客户端证书，可选同时导出 `.pfx`
- 证书库视图：列出输出目录里的全部证书，显示到期情况
- 吊销：维护一份指纹名单，导出成 web_ics 能读的 `deny.txt`
- 生成 `web_ics.conf` 片段
- 单文件 EXE，双击可用

### 不打算做的

- 不改 web_ics 的代码，两边只通过文件与配置约定对接
- 不做在线服务、不做多用户、不做权限管理
- 不做证书热加载或服务重启——那是使用者的操作
- 不实现 CRL 与 OCSP（web_ics 的 TLS 栈不做这项检查，用纯文本名单代替）

## 三、技术选型

### 待定的选型

先列出候选，动手前用一个小 demo 验证，验证不过就换。

| 维度 | 候选 | 倾向 | 待验证的点 |
|---|---|---|---|
| 语言 | Go / Rust | **Go** | 能否直接复用 ICS 仓库里已经跑通的证书参数 |
| 界面 | 本地网页 / 原生控件 / Electron / Tauri | **本地网页** | 表单 + 表格的界面，网页最省事，改样式不用重编译 |
| 窗口 | 内嵌 WebView2 / Edge 应用模式 / 系统浏览器 | **内嵌 WebView2** | 在目标机器上能否稳定创建窗口 |
| 证书库 | `crypto/x509` / 调用 openssl | **`crypto/x509`** | 不依赖外部程序，产出可控 |
| `.pfx` | 标准库 / 第三方 | **`go-pkcs12`** | 标准库不提供 PKCS#12 编码 |

**语言先定 Go 的理由**：web_ics 本身是 Go，证书参数可以直接对着它的文档与测试抄，
不用重新推导一遍；产物是单文件，没有运行时依赖。

### 预计引入的依赖

尽量少。目前只预计需要三个：

| 依赖 | 用途 | 是否可省 |
|---|---|---|
| `software.sslmate.com/src/go-pkcs12` | 导出 `.pfx` | 不可省，标准库没有 |
| `github.com/jchv/go-webview2` | 内嵌窗口 | 若选型改为 Edge 应用模式则可省 |
| `golang.org/x/sys` | Win32 调用 | 不可省，但只是薄封装 |

### 界面技术

原生 HTML/CSS/JS，不引框架、不加构建步骤。界面规模不大（七个页签、十几个输入框），
构建链的维护成本抵不上收益。

## 四、架构设想

单进程，三块：

1. **内置 HTTP 服务**，只监听回环地址，端口由系统分配。网页资源用 `go:embed` 打进二进制。
2. **窗口**，指向上面那个服务。
3. **领域逻辑**，按职责分三个包。

```
internal/certs     证书领域逻辑（不认识 HTTP，也不认识界面）
internal/validate  字段校验规则 + 字段说明表
internal/app       HTTP 服务、状态、配置片段
ui/                界面（构建时嵌进二进制）
```

分层规则：`certs` 不依赖 `app`，`app` 依赖 `certs` 与 `validate`。
新增签发能力落点在 `certs`，`app` 只做参数搬运和错误翻译。

### 几条先定下来的设计约束

- **证书库不存索引，每次扫磁盘。** 索引与磁盘不同步是最难查的一类问题。
- **校验规则只有一份。** 界面不重抄一遍，输入变化时回服务端问。
- **重名不覆盖。** 第二次签同名证书得到 `-2` 后缀。覆盖的后果很隐蔽：私钥被换掉，
  旧证书还在设备上装着，两边指纹对不上。
- **子证书有效期卡在 CA 剩余有效期之内。** 签发者过期会让子证书一起失效，
  而现象是「证书看着完好、浏览器却拒绝」。
- **服务只监听回环地址。** 界面是本机工具，不对外。

## 五、阶段划分

### 阶段 0：技术选型验证（预计 1–2 天）

不动业务代码，只回答「这条路走不走得通」。

| 任务 | 产出 | 通过标准 |
|---|---|---|
| 用 Go 建一张自签名 CA，签一张证书 | 一段能跑的 demo | openssl 能验过链，SAN 与 KeyUsage 正确 |
| 对比 ICS 仓库的证书参数 | 参数对照表 | 逐项对齐，差异能解释 |
| 试内嵌 WebView2 开窗口 | demo 窗口 | 目标机器上能开出来，关掉后进程能退干净 |
| 试单文件打包 | 一个 EXE | 拷到别的目录仍能跑 |

**这一阶段的产出是一份选型结论**：确认或推翻上面的倾向，并记录为什么。

⚠️ 这一阶段要特别注意：**在本机跑通不等于在用户机器上跑通**。窗口、DPI、证书库这些
跟系统状态相关的东西，要在干净的机器上复验一遍再下结论。

### 阶段 1：证书核心（预计 3–5 天）

`internal/certs`，先把命令行能跑通，界面之后再说。

- 密钥与序列号生成
- 建 CA / 加载 CA（含自检：证书与私钥是否配对、是否 CA、是否过期）/ 导入 CA
- 签服务器证书：SAN 分流成 IP 与 DNS，两者都为空时拒绝签发
- 签客户端证书：`KeyUsage` 含 `digitalSignature`，EKU 含 `clientAuth`
- 导出 PKCS#12（用 Modern 方案，不用 RC2/3DES）
- 扫描目录、判定证书角色、算指纹
- 吊销名单的格式化与写文件
- 文件名清洗与重名避让

**验收标准**：

- 签出的证书能被 openssl 验过链，SAN / KeyUsage / EKU 与预期一致
- 客户端证书能通过 web_ics 服务端的判定口径（链能验过 + EKU 含 clientAuth +
  KeyUsage 含 digitalSignature）
- 同一名字签两次，得到两个文件，内容不同
- 私钥与证书不配对时，加载阶段就报错，而不是签出一堆验不过的证书
- 已过期的 CA 被拒绝加载

### 阶段 2：校验规则（预计 2–3 天）

`internal/validate`。这一层是「用户填错时能不能早点知道」的关键。

- 名字类字段：非空、首尾无空格、长度上限、禁用字符
- 地址类字段：识别 IP 与域名；拦掉协议前缀、端口、路径、通配符
- 有效期：范围检查 + 不能超过 CA 剩余有效期
- 证书包密码：导出时必填、长度下限
- 字段说明表 `Catalog()`，同时喂给界面和文档

**验收标准**：

- 每条规则都有一句能照着改的错误文案
- 地址里的 `https://`、`:8443`、`/path` 被拦下并说明去掉哪一段
- 内网地址允许单段名（`nas`），外网地址要求至少两段
- 同一份证书里的重复地址被拦下

### 阶段 3：本地服务与接口（预计 3–4 天）

`internal/app`。

- 起服务、挑端口、会话令牌与 cookie 校验
- 状态组装：扫目录、比对吊销名单、算到期情况、生成配置片段
- 状态文件读写（输出目录 + 吊销名单）
- 各接口：spec / state / validate / settings / ca / issue / revoke / unrevoke /
  export deny / conf / reveal / quit

**验收标准**：

- 不带令牌访问 `/api/` 下的任何接口被拒
- 服务只监听回环地址，外部地址连不上
- 改设置、签发、吊销之后，响应里带的最新状态与单独请求 `/api/state` 一致
- 状态文件解析失败时拒绝启动，不静默重置

### 阶段 4：界面（预计 4–6 天）

`ui/`。七个页签：概览、根 CA、服务器证书、客户端证书、证书库、吊销名单、配置对接。

- 输入框下面的帮助文本由 `/api/spec` 填充
- 输入实时校验（防抖），错误按字段标红
- 签发结果卡片、证书库表格、吊销名单列表
- 概览页按进度提示「下一步」

**验收标准**：

- 七个页签都能走通，不出现点了没反应
- 每个输入框都能看到用途、格式、示例与校验规则
- 校验失败时错误落在对应的输入框上，不是笼统的一条提示
- 证书多、窗口窄时不出横向滚动条

### 阶段 5：窗口与平台壳（预计 3–5 天）

根目录那组平台文件。

- 内嵌窗口、DPI 感知、单实例、错误弹框、打开浏览器的退路
- 非 Windows 平台留空实现，保证能交叉编译

**验收标准**：

- 双击 EXE 直接出窗口，没有控制台
- 窗口关掉之后，进程与子进程都退出
- 再双击一次不会开出第二个窗口，而是把已有的叫到前面
- 内嵌窗口创建失败时能退回系统浏览器，并把原因告诉用户
- 非 Windows 平台能编过（不需要能跑界面）

### 阶段 6：构建、打包与文档（预计 2–3 天）

- 构建脚本（Windows 与其他平台各一份），产出单文件 EXE
- 校验产物里没有构建机路径
- README、字段说明文档
- 发布包与许可证

**验收标准**：

- 两个构建脚本产出的二进制逐字节相同
- 产物拷到干净目录仍能跑
- 文档里的步骤按着做能走通

### 阶段 7：验收（预计 1–2 天）

对着 web_ics 实际跑一遍完整流程：建 CA → 签服务器证书 → 部署到服务器 → 给两台设备签客户端
证书 → 装证书 → 浏览器访问 → 吊销一台 → 写出名单 → 重启服务 → 确认被拒。

**这是唯一能证明「工具真的解决了问题」的一步**，前面所有阶段的验收都只是局部正确。

## 八、开发顺序与理由

**先做能验证的部分，再做界面。** 证书核心正确与否有客观标准（openssl 能验、web_ics 能认），
可以先在命令行上把这条路走通。界面做得再好看，签出来的证书服务端不认也是白搭。

**校验规则紧跟证书核心。** 界面的实时校验依赖它，而且它是「用户填错时能不能早点知道」
的关键，不该等到最后补。

**窗口与打包放在界面之后。** 这两块的风险在于平台细节，而平台细节可以在选型验证阶段
先把最大的不确定性（能不能开窗口）排掉。

**端到端验收放在最后，但要在 M0 阶段就准备好环境**：一台能跑 web_ics 的服务器、
两台能装证书的设备。这一步卡住会拖住整个项目。

## 九、风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 内嵌窗口在目标机器上不稳定 | 阶段 5 可能推翻 | 阶段 0 先验证；保留「退回系统浏览器」的退路 |
| 证书参数与 web_ics 不一致 | 签出来的证书服务端不认，且现象不直观 | 阶段 0 就对参数表；阶段 1 按 web_ics 的判定口径做验收 |
| 进程退出不干净 | 用户体验差（任务管理器里留一堆进程） | 阶段 0 就测；实在不行改用系统浏览器模式 |
| 跨平台分支腐化 | 非 Windows 编不过 | 构建脚本里加一步交叉编译检查 |
| 重名覆盖 | 私钥被换掉，旧证书还在设备上，排查无线索 | 一律不覆盖，加后缀 |
| CA 被误覆盖 | 已装旧 CA 的客户端全部连不上 | 目录里已有 CA 时拒绝再建，要求先移走 |
| 端到端验收环境不到位 | 阶段 7 卡住 | 项目一开始就准备服务器与测试设备 |
| 界面改动牵动服务端 | 接口与字段名两边对不上 | 接口与字段名写成表，两边对照维护 |

## 十、待定问题

动手前需要定下来，或者在前几个阶段里回答：

1. 目标机器上 WebView2 运行时的覆盖率如何？缺了能不能接受「退回浏览器」这个降级？
2. 是否需要支持 Linux / macOS？如果只是「能编过」，那非 Windows 的窗口实现可以先不做。
3. 证书库的排序按什么？目前倾向「先按角色、同角色按到期时间」，让最该处理的排最前。
4. 吊销名单要不要支持导入？导出的格式是确定的，导入需要考虑格式校验与合并策略。
5. 需不需要代码签名？不做的话首次运行会有 SmartScreen 提示。
